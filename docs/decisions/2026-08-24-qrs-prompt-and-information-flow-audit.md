# QRS prompt and information-flow audit

Date: 2026-08-24
Status: read-only audit retained; main execution remains `NO-GO`
Audit baseline: committed revision `71df57e` plus the separately tested local
S6-Core construct files

## Intended story and executable contract

The intended method is a QRS-only cumulative harness-evolution lineage:

```text
fresh Quant-H0-S6-Core
  -> public task, data, Worker trajectory, and answer-free eligible history
  -> QRS State Card and state-conditioned retrieval/routing
  -> complete candidate harness plus claim inventory and transition prediction
  -> Candidate Information-Set Review of exact effective candidate
  -> PASS
  -> exact reviewed snapshot reaches a blind Worker
  -> official target -> independent repeat -> answer-free protection
  -> frozen incumbent -> sealed no-feedback evaluation
```

The six-state Core interface is fixed human instrumentation. The Evolver owns
the implementation of stage capabilities. The Candidate Reviewer reviews the
candidate information set, not the Worker answer, and has no mutation,
evaluation, retention, or promotion authority. QRS-no-State and AHE are
separate executables; neither is a runtime arm in the released QRS method.

## What already matches

- Rootless QFBench separates Worker and verifier bundles. Public task files go
  to the Worker; official tests and solution material go only to the verifier.
- The trusted Worker contract allows a rule stated by the public instruction,
  supplied public data, or a predeclared public reference, while forbidding
  hidden checker behavior, expected answers, official property identities,
  prior scores, and unstated benchmark constants.
- The public-trajectory builder can produce an answer-free initial QRS view
  with a fresh Worker trace/final/artifacts, protection contracts, empty
  component history, and no score, verifier, optimization diagnostic, or prior
  candidate episode.
- When Candidate Information-Set Review is explicitly enabled, it inspects
  candidate files/diff, structured claims, support, and coverage. Real holdings
  Review `INCONCLUSIVE`/`REJECT` results correctly produced
  `HOLD_FOR_REFINE` and zero Worker dispatch.
- Target Worker argv does not contain Reviewer reasons or optimize-only
  diagnostic paths.

These are useful pieces, but they are not yet one universal executable
invariant.

## Worker prompt audit

### Keep in S6-Core

- the reusable-harness rather than task-answer objective;
- the public-versus-hidden rule;
- S1--S6 names and concise public markers;
- public-grounded `NOT_APPLICABLE`;
- S5 revisit syntax; and
- the statement that marker coverage is not correctness.

### Keep out of the fixed substrate

The existing S6-Full additionally instructs the Worker to inspect detailed
data-quality fields, write structurally valid artifacts early, use independent
examples or perturbations, and run explicit schema/finite-value/reconciliation
checklists. These may be good quantitative practice, but they implement stage
behavior that QRS is supposed to evolve. They remain a disclosed human-workflow
baseline, not the default QRS parent.

The trusted runtime rule is defense in depth, not enforcement. A prompt saying
"do not use hidden answers" cannot prove that an evolved tool or skill did not
encode one.

## Evolver prompt and evidence audit

The existing `evolve_agent_full` prompt is a multi-protocol superset. It mixes
legacy A6 discovery, Generic, quant-state, quant-state-v2, answer-rich
QuantCodeEval, lineage refinement, selected-probe instructions, and the current
QRS State Card path. The common component-view builder likewise accepts
Generic/QRS arms and answer-rich optimization diagnostics.

That flexibility was useful during development but is not the claimed main
method. The main executable needs a dedicated QRS profile that:

- accepts only `method=qrs`, not a Generic/QRS arm switch;
- binds a frozen QRS Evolver implementation;
- requires public/answer-free evidence and rejects optimization diagnostics;
- requires a State Card, selected expected--observed--target transition,
  component locus, competing explanation, and falsifiable observation;
- requires a complete structured Worker-visible claim inventory for every
  `ACT`;
- emits a candidate harness only, with no separate Evolver-authored Worker
  directive; and
- never dispatches a selected probe from the proposal runner.

QRS-no-State needs a separately frozen profile that removes state-conditioned
construction/retrieval/routing while keeping all other lifecycle controls
fixed. AHE needs a pinned upstream reproduction and separately disclosed
quantitative adapter, outside the QRS code path.

## Candidate Reviewer audit

The Reviewer rubric is conceptually aligned: public support can make a claim
eligible; diagnostic-only origin, public contradiction, or undeclared exposure
blocks it; `PASS` grants evaluation permission only.

The current implementation does not yet review the exact effective candidate:

1. Review is opt-in; legacy and preconstructed candidate paths can enter
   `TARGET` without it.
2. Review material defaults to the immediate parent instead of the lineage's
   original S6-Core baseline.
3. The controller accepts plan-authored public excerpts without re-reading the
   frozen public file.
4. Candidate material is read from a mutable directory. A Review-`PASS`
   candidate can change before Worker dispatch.
5. A reused `RESULT.json` is bound to IDs and claim labels, not the complete
   candidate and public-source material.
6. The universal Reviewer prompt contains historical SVI/pair-serialization
   examples from contamination analysis. Those should be synthetic and
   benchmark-independent in the public-only main Reviewer.
7. The reviewed filesystem tree excludes post-admission Worker instructions
   and other effective runtime overlays.

The central claim should therefore be **candidate-focused uniform
information-set review**, not `arm-blind`. Candidate content may reveal QRS;
uniform criteria and lack of outcome/mutation/promotion authority are the
scientifically relevant properties.

## Controller and result-binding audit

The discovery selected-probe path can copy an admitted candidate, change its
iteration budget, append an Evolver-authored Worker instruction, and directly
evaluate it without Candidate Review. Other component-pilot and older
QFBench/QuantCodeEval entrypoints also accept candidate directories directly.

Even on the intended lineage path, Review PASS leaves only a mutable
`worker_dir`; the target runner later reads that live directory. Existing
target reports can be imported by run ID without proving that their Worker was
the reviewed snapshot. Thus neither candidate material nor official result is
currently bound end to end.

The main controller must materialize one immutable effective snapshot before
Review. That snapshot contains cumulative S6-Core-to-candidate harness
surfaces, effective agent bindings, the fixed trusted runtime overlay, public
task instruction identity, and any other Worker-visible prestage. Reviewer and
Worker must read that same snapshot. Existing Review and Worker results may be
resumed only when their complete stored inputs match the current package.

## Public evidence and history audit

The public trajectory builder needs ordinary, reconstructable identity checks:

- bind the fresh attempt to the supplied S6-Core Worker;
- parse `agent.yaml` to confirm the S6 skill is registered rather than merely
  present as a file;
- read target/protection contracts from verified public task roles;
- allowlist process-summary fields; and
- fail closed if the six-state protocol is not actually realized when a run is
  advertised as state-indexed S6-Core evidence.

Main history starts empty. Only prospectively public-only, Review-PASS,
officially evaluated episodes may enter QRS history through an explicit
allowlist. The six retrospectively contaminated candidates and trusted
controller property identities never enter retrieval.

## P0 order before one QRS candidate

1. Freeze the dedicated QRS-only public/answer-free Evolver profile.
2. Fix S6-Core attempt/public-role identity and state-protocol validation.
3. Make proposal generation proposal-only; remove main selected-probe dispatch
   and external Worker directives.
4. Materialize the immutable cumulative effective candidate snapshot.
5. Build Reviewer public support by trusted file reads and bind Review result to
   the complete package.
6. Require Review PASS at the actual Worker-dispatch choke point; forbid
   preconstructed/main candidate bypass.
7. Bind target/repeat/protection reports to the reviewed snapshot before
   importing official observations.
8. Test missing Review, modified-after-Review, stale Review result, fake public
   excerpt, selected-probe, and stale target-report failures.
9. Run one fresh public-only chain:

   ```text
   S6-Core -> QRS ACT -> Review PASS -> exact blind Worker -> strict gain
   ```

This closes one operational answer-boundary example, not stable promotion.
Independent repeat and answer-free protection are still required before a
candidate is retained.

## Experimental reporting boundary

Development task families may be chosen deliberately for mechanism
observability, runtime validity, headroom, and protection availability. The
eligible pool, inclusion/exclusion rules, family roles, selected tasks, and
freeze time must be disclosed. Hiding deliberate selection is not acceptable.
Population or generalization claims come only from a separately frozen,
family-stratified sealed panel that never feeds search.

Development reporting uses every predeclared opportunity in the stable-
promotion denominator and shows the full task/property vector. Final reporting
shows the complete sealed vector plus task and equal-family summaries. AHE is
compared on common sealed outcomes and resource use, not forced into QRS's
internal promotion semantics.
